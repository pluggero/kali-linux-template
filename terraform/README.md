# Terraform Configuration for Kali Linux VirtualBox Deployment

This directory contains Terraform configurations for deploying Kali Linux VMs built with Packer to VirtualBox using **VBoxManage** directly.

## Architecture

```
terraform/
├── modules/
│   └── virtualbox-vm/      # Reusable VM deployment module
│       ├── main.tf          # VBoxManage-based VM provisioning
│       ├── variables.tf     # Module input variables
│       └── outputs.tf       # Module outputs
├── environments/
│   ├── dev/                 # Development environment
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   ├── outputs.tf
│   │   └── terraform.tfvars.example
│   └── prod/                # Production environment
│       ├── main.tf
│       ├── variables.tf
│       ├── outputs.tf
│       └── terraform.tfvars.example
└── versions.tf              # Provider version constraints
```

## How It Works

Unlike typical Vagrant-based deployments, this implementation uses **VBoxManage** directly for better compatibility with Packer-built images:

1. **Import**: Imports the OVF file (generated by Packer) using `VBoxManage import`
2. **Configure**: Applies VM settings (CPU, memory, network, graphics) via `VBoxManage modifyvm`
3. **Start**: Launches the VM in headless mode using `VBoxManage startvm`
4. **Monitor**: Retrieves VM IP from VirtualBox guest properties

This approach avoids Vagrant's SSH user requirements and works seamlessly with your Packer-built Kali images.

## Prerequisites

1. **Terraform** (>= 1.0)
2. **VirtualBox** with VBoxManage CLI
3. **Packer-built Kali Linux image** (OVF + Box files in `packer/outputs/`)

**Note**: Vagrant is NOT required for this implementation.

## Quick Start

### 1. Deploy Using the Helper Script (Recommended)

From the repository root:

```bash
# Deploy to dev environment (VM only)
./scripts/kali_deploy.sh dev apply

# Deploy with automatic post-configuration
./scripts/kali_deploy.sh dev apply true

# Deploy to prod environment
./scripts/kali_deploy.sh prod apply
```

The script automatically:
- Finds the latest Packer-built OVF/box file
- Extracts version and build date from directory name
- Initializes Terraform if needed
- Deploys the VM with proper configuration
- Optionally runs post-deployment Ansible playbooks

### 2. Manual Deployment

If you prefer manual control:

```bash
cd terraform/environments/dev

# Copy and edit configuration
cp terraform.tfvars.example terraform.tfvars
nano terraform.tfvars

# Initialize Terraform
terraform init

# Review the plan
terraform plan \
  -var "box_file=/path/to/kali.box" \
  -var "vm_version=2025.3" \
  -var "vm_build_date=20251021"

# Apply
terraform apply \
  -var "box_file=/path/to/kali.box" \
  -var "vm_version=2025.3" \
  -var "vm_build_date=20251021"
```

## Configuration Variables

### Common Variables

| Variable | Description | Default |
|----------|-------------|---------|
| `vm_name` | Name of the VM | `kali-linux-dev` / `kali-linux-prod` |
| `vm_version` | Kali version | `2025.3` |
| `vm_build_date` | Build date (YYYYMMDD) | Auto-detected |
| `box_file` | Path to .box file | Auto-detected from packer/outputs |

### Hardware Configuration

| Variable | Description | Default |
|----------|-------------|---------|
| `cpus` | Number of CPU cores | `3` |
| `memory` | RAM in MB | `8192` |
| `vram` | Video RAM in MB | `256` |

### Network Configuration

| Variable | Description | Default |
|----------|-------------|---------|
| `bridged_adapter` | Network interface to bridge | `pentap0` |

**Important**: Update `bridged_adapter` to match your network interface. List available interfaces:
```bash
VBoxManage list bridgedifs
```

### Display Configuration

| Variable | Description | Default |
|----------|-------------|---------|
| `graphics_controller` | Graphics controller type | `vmsvga` |
| `clipboard_mode` | Clipboard sharing mode | `bidirectional` |

### Post-Deployment Configuration

| Variable | Description | Default |
|----------|-------------|---------|
| `run_post_deploy` | Auto-run Ansible post-config | `false` |
| `post_deploy_script` | Path to post-deploy script | `../../../scripts/kali_post_deploy.sh` |

## Deployment Options

### Option 1: Deploy Only (Default)

Deploy the VM infrastructure without configuration:

```bash
./scripts/kali_deploy.sh dev apply
```

Then manually run post-configuration when ready:
```bash
./scripts/kali_post_deploy.sh
```

**Best for**: Development, testing, when you want control over when to configure.

### Option 2: Deploy + Auto-Configure

Deploy and automatically run Ansible post-configuration:

```bash
./scripts/kali_deploy.sh dev apply true
```

**Best for**: CI/CD pipelines, automated deployments, production.

### Option 3: Configure via terraform.tfvars

Set in `terraform.tfvars`:
```hcl
run_post_deploy = true
```

Then deploy normally:
```bash
cd terraform/environments/dev
terraform apply
```

**Best for**: Persistent configuration, team consistency.

## Managing VMs

### Get VM IP Address

```bash
VM_NAME="kali-linux-dev-dev"
VBoxManage guestproperty get "$VM_NAME" /VirtualBox/GuestInfo/Net/0/V4/IP
```

Or use Terraform output:
```bash
cd terraform/environments/dev
terraform output vm_info
```

### Access the VM via SSH

Once you have the IP address:
```bash
ssh kali@<VM_IP>
```

Use your configured SSH keys (from Ansible vault).

### Check VM Status

```bash
VBoxManage showvminfo "kali-linux-dev-dev" --machinereadable | grep VMState
```

### Stop the VM

Using Terraform:
```bash
./scripts/kali_deploy.sh dev destroy
```

Or manually:
```bash
VBoxManage controlvm "kali-linux-dev-dev" poweroff
```

### Start the VM

```bash
VBoxManage startvm "kali-linux-dev-dev" --type headless
```

### Destroy the VM

Using the helper script:
```bash
./scripts/kali_deploy.sh dev destroy
```

Or manually:
```bash
cd terraform/environments/dev
terraform destroy
```

This will:
1. Power off the VM
2. Unregister and delete it from VirtualBox
3. Clean up Terraform state

## Environment Separation

### Development Environment
- **Location**: `terraform/environments/dev/`
- **Purpose**: Testing, development, experimentation
- **VM Name**: `kali-linux-dev-dev`
- **Lifecycle**: Short-lived, frequently rebuilt

### Production Environment
- **Location**: `terraform/environments/prod/`
- **Purpose**: Production-ready deployments, long-running VMs
- **VM Name**: `kali-linux-prod-prod`
- **Lifecycle**: Long-lived, stable

## Workflow Integration

### Complete Build → Deploy → Configure Workflow

```bash
# 1. Build the image with Packer
./scripts/kali_provision.sh

# 2. Deploy with Terraform (infrastructure only)
./scripts/kali_deploy.sh dev apply

# 3. Configure with Ansible (when ready)
./scripts/kali_post_deploy.sh
```

Or all-in-one:
```bash
# Build
./scripts/kali_provision.sh

# Deploy + Configure
./scripts/kali_deploy.sh dev apply true
```

### Separation of Concerns

- **Packer**: Creates immutable VM images (build phase)
- **Terraform**: Manages VM infrastructure lifecycle (deploy phase)
- **Ansible**: Configures running VMs (configure phase)

This separation allows:
- Rebuilding images without redeploying
- Redeploying VMs without rebuilding images
- Reconfiguring VMs without redeploying

## Best Practices

1. **Version Control**: Never commit:
   - `terraform.tfvars` (contains environment-specific values)
   - `*.tfstate` and `*.tfstate.*` (state files)
   - `.terraform/` (provider cache)
   - `.terraform_vagrant_*/` (runtime directories)

2. **Environment Isolation**: Use separate directories for dev/prod to prevent accidental deployments

3. **Box File Management**: Let the deployment script auto-detect the latest box file

4. **Network Configuration**: Always verify and update `bridged_adapter` to match your network interface

5. **State Management**: For team collaboration, consider using remote state (S3, Terraform Cloud)

6. **Post-Deployment**:
   - Use manual post-deploy for development (more control)
   - Use automatic post-deploy for CI/CD (full automation)

## Troubleshooting

### VBoxManage Command Not Found

Ensure VirtualBox is installed and in your PATH:
```bash
which VBoxManage
# Should return: /usr/bin/VBoxManage (or similar)
```

### OVF File Not Found

Error: `No such file: /path/to/file.ovf`

**Solution**: Ensure Packer build completed successfully:
```bash
ls -la packer/outputs/kali-linux-*/
# Should show .ovf, .box, and .vmdk files
```

### VM Import Fails

Error: `Failed to import OVF`

**Solution**: Check if VM with same name exists:
```bash
VBoxManage list vms
# If exists, remove it:
VBoxManage unregistervm "kali-linux-dev-dev" --delete
```

### VM Won't Start

Error: `Failed to start VM`

**Solutions**:
1. Check VirtualBox logs:
   ```bash
   VBoxManage showvminfo "kali-linux-dev-dev" --log 0
   ```

2. Verify virtualization is enabled in BIOS

3. Check for conflicting VMs:
   ```bash
   VBoxManage list runningvms
   ```

### Can't Get VM IP Address

Issue: IP address shows as "No value set"

**Causes & Solutions**:
1. **VM not fully booted**: Wait 30-60 seconds and retry
2. **Guest Additions not installed**: Packer should install these; verify in VM
3. **Network not bridged**: Check VM network settings:
   ```bash
   VBoxManage showvminfo "kali-linux-dev-dev" | grep NIC
   ```

### SSH Connection Refused

Issue: Can't SSH to VM even with correct IP

**Solutions**:
1. Check SSH service is running (check via VirtualBox console)
2. Verify firewall rules allow SSH
3. Ensure SSH keys are properly configured (check Ansible vault)
4. Test with password auth first (if enabled)

### Network Bridge Issues

Error: `Invalid bridgeadapter`

**Solution**: List available interfaces and update config:
```bash
VBoxManage list bridgedifs
# Update terraform.tfvars with correct interface name
```

### Terraform State Locked

Error: `Error acquiring the state lock`

**Solution**:
```bash
cd terraform/environments/dev
terraform force-unlock <LOCK_ID>
```

### VM Already Exists in Different Environment

Issue: VM name collision between dev/prod

**Solution**: Each environment uses different VM names:
- Dev: `kali-linux-dev-dev`
- Prod: `kali-linux-prod-prod`

If collision still occurs, check and remove:
```bash
VBoxManage list vms
VBoxManage unregistervm "<name>" --delete
```

## Advanced Usage

### Custom VM Configuration

To customize VM settings beyond variables, edit the module:
- `terraform/modules/virtualbox-vm/main.tf`

Example: Add USB support:
```hcl
provisioner "local-exec" {
  command = <<-EOT
    VBoxManage modifyvm "${local.vm_full_name}" \
      --usb on \
      --usbehci on
  EOT
}
```

### Multiple VMs in Same Environment

Deploy multiple VMs by creating additional module instances:

```hcl
# In terraform/environments/dev/main.tf

module "kali_vm_1" {
  source = "../../modules/virtualbox-vm"
  vm_name = "kali-linux-dev-1"
  box_file = local.latest_box_file
  # ... other vars
}

module "kali_vm_2" {
  source = "../../modules/virtualbox-vm"
  vm_name = "kali-linux-dev-2"
  box_file = local.latest_box_file
  # ... other vars
}
```

### Remote State for Team Collaboration

Configure remote state backend in `main.tf`:

```hcl
terraform {
  backend "s3" {
    bucket = "my-terraform-state"
    key    = "kali-linux/dev/terraform.tfstate"
    region = "us-east-1"
  }
}
```

Or use Terraform Cloud:
```hcl
terraform {
  cloud {
    organization = "my-org"
    workspaces {
      name = "kali-linux-dev"
    }
  }
}
```

### Conditional Post-Deployment

Run different post-deploy scripts based on environment:

```hcl
# In environments/dev/main.tf
module "kali_vm" {
  source = "../../modules/virtualbox-vm"
  # ...
  run_post_deploy = true
  post_deploy_script = "../../../scripts/kali_post_deploy_dev.sh"
}

# In environments/prod/main.tf
module "kali_vm" {
  source = "../../modules/virtualbox-vm"
  # ...
  run_post_deploy = true
  post_deploy_script = "../../../scripts/kali_post_deploy_prod.sh"
}
```

## Architecture Decisions

### Why VBoxManage Instead of Vagrant Provider?

1. **Compatibility**: Packer-built images use custom user (`kali`), not Vagrant's expected `vagrant` user
2. **Simplicity**: Direct VBoxManage calls are more transparent and easier to debug
3. **Control**: Full control over VM configuration without Vagrant abstractions
4. **Performance**: No SSH connection overhead during deployment

### Why Separate Post-Deployment?

1. **Flexibility**: Choose when to run configuration (immediate vs. later)
2. **Debugging**: Easier to troubleshoot infrastructure vs. configuration issues
3. **Re-runnability**: Can re-run Ansible without redeploying VM
4. **Best Practice**: Terraform for infrastructure, Ansible for configuration
